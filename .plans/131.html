What changes for users

  • Triage panel → Coverage and permissions: one status per feature (Triage and Tags, Beyond this page: Full / Limited / Not in use / Off), the issue's notes 1–8 in order, and one action line at the foot. With the engine off, only the hint “Tokens and permissions: Settings → GitHub tokens”.
  • Inbox: at most one quiet line in the Triage block, under the coverage lines, when Unverifiable rows come from an owner that can't be read (“15 from acme are Unverifiable: no token can read acme. How to fix this ›”). Its link opens the panel scrolled to Coverage.
  • Settings → GitHub tokens: a full-width Notifications block (#tokens-more) between + Add token and the guide: the check “Your full notifications list”, By owner, What each notifications feature needs, and the four-step how-to.
  • Test on the default token makes one extra read (GET /notifications); Access denied makes the token Missing permissions only while Triage or Tags is on, and the warning gets the release sentence.
  • Fine-grained default tokens are never told to switch: Not verified, out of the count, no how-to.

Data, permissions, privacy

Token permissions: none. No new token scope, permissions or host_permissions. The classic notifications scope stays optional and is only explained. Storage: no new key. The check's outcome code joins the existing ghrTokenTests session record (codes only). The owner passed to Settings travels in the extension URL only (validated login, never a token) and is never stored. Requests: opening the panel or Settings sends none; Test on the default token sends one more read-only GET /notifications?per_page=1; nothing is written to GitHub. PRIVACY.md names that extra read.

Docs and release notes

Release Please builds the changelog and the GitHub Release from the squash commit, i.e. the PR title, under a heading that is the release number. So the release notes are covered in three places, all written in the implementation PR:

  • PR title (= the changelog and release line): feat: explain why notifications are limited and that the classic notifications permission is optional (this PR's title is updated now).
  • PR body: a ## Release notes section, e.g. “From {X}: the inbox, the Triage panel and Settings → GitHub tokens explain why a notification is limited. The classic token permission notifications stays optional: without it everything on the loaded page keeps working; Test on the default token now checks it.”
  • README and PRIVACY.md: the same two facts (optional permission, release {X}).

{X} = the version of the open Release Please PR at hand-off, or, if none is open, the next minor of manifest.json's version (a feat bumps minor: 1.7.0 → 1.8.0); re-checked after the rebase before marking ready. The in-product warning still reads {X} from the manifest at runtime (as the issue requires), not from this text. Checked by the token-docs.test.js row above for README and PRIVACY, and, before gh pr ready, by gh pr view <N> --json title,body asserting the title contains “notifications permission is optional” and the body has ## Release notes naming notifications, “optional” and {X}; the result is listed under the PR's acceptance criteria.

Assumptions

  • No default token and no owner recorded (api: not-tried, no loaded row needs facts): the issue's status table (row 4, “including when no owner is recorded”) and its Degraded table (“No token: Triage and Tags Limited”) disagree. Reading taken: Triage and Tags Full, Beyond this page Not in use, and only note 5 (first sentence only, since no owner is ok; note 8 and every action line left out, as the acceptance criterion “only note 5 shows” is the more specific rule) — rejected: Limited, because nothing on the loaded page is actually limited (no row is Unverifiable), the status table is the explicit first-match rule, and a Limited label would read as something to fix when nothing is required; the Degraded row describes the usual case where rows need facts and owners are no-token (then Limited + note 2). This cell is asserted by name in the “status matrix” unit test and in the e2e “no token, no owner”.
  • Slot id: the tokens page reserved #notifications-permission-slot, the issue names tokens-more and “no second id”: rename the slot to tokens-more — rejected: keeping both ids, because the issue asks for one.
  • Engine states: #126's refused and no-answer read as unavailable here — rejected: new notes for them, because the issue lists “another 403 or no answer” under unavailable.
  • Inbox line host: only while Triage runs (it lives in the Triage block) — rejected: a separate line for Tags-only, because it would need a new anchor on GitHub's markup and the tag's own panel already explains Unverifiable.
  • Release {X}: the installed manifest version (Release Please owns it), as the #129 warning already does — rejected: a hand-kept constant, because the issue forbids literals.
  • Fine-grained default: no notifications request is sent (at most one, never for a local fine-grained prefix) — rejected: always sending it, because the outcome is fixed by GitHub's rule.
  • By owner: lists owner tokens plus, when Settings was opened from an owner action, that owner (URL only); prefill = Owner field only — rejected: storing inbox owners, because no new key is allowed.
  • How-to visibility: shown for classic or no default token (open when Access denied or via “How to add it”), hidden for fine-grained and when Available.
  • Test vs 60 s cache: Test uses its own direct fetch (no cache), so the last step needs no “wait a minute”; the inbox picks the change up after a reload (note 8).

Risks and open questions

  • GitHub's 403 for a classic token without notifications may not carry x-accepted-oauth-scopes (default: then it reads Not verified, never Access denied).
  • Panel height grows with notes at 320 px (default: panel already scrolls inside max-height; openAt scrolls the Coverage heading to the top).
  • Many owners (default: cap 3 + “and N more”, one action line each, as the issue says).
  • Reading test with three people is outside an agent's reach (default: listed under “Not verified” for the maintainer).

Out of scope

  • Reading the notifications list with owner tokens; repository or owner discovery.
  • Changing the tokens page mechanics, words or the multi-page triage lines and reads.
  • The shipped text of the “Why is this here?” switch.
  • A docs/releases/ page: the repository has none; release notes are the Release Please changelog (see “Docs and release notes”).
