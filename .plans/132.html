#132 · Copy gh command and adaptive Open raw log on Actions run and job pages

Issue cattanisimone/gh-reloaded#132 · Size: normal (new UI surface, new feature, Options and token docs) · Goal: two shortcuts to a run's or job's logs, no log bytes ever in the extension, no new permission.

What changes for users

  • New feature Actions log shortcuts, on by default, one switch in Options → Features.
  • Run and job pages: a Copy gh command button above the content copies e.g. gh run view --log-failed --job 132076068976 --repo OWNER/REPO; "Copied" / "Copy failed" is announced, and on failure the command stays visible and selectable.
  • Job pages only: Open raw log next to it, only when the user's token proves it can read that repository's Actions logs (one read probe per repository and token per minute). It opens the page's own "View raw logs" link in a new tab.
  • No message on Actions pages in any state. When the last check for an owner was not-permitted, Options shows a warning in Features and on the token card used for that owner; Options → GitHub tokens lists Actions: Read-only as optional.

How it works

GitHub answer to the probe (with a token)StateStored / Options warning
opaque redirect (302) or 2xxokok; clears the owner's warning
403 / 404, no rate-limit, no X-GitHub-SSOnot-permittednot-permitted; warning
403 / 429 with remaining 0 or Retry-After (existing rateInfo)rate-limitedunchanged; no request before retryAt
403 with X-GitHub-SSO, 401, 410, 5xx, network, anything elseunknownunchanged; retried after 60 s
no token resolved for the owner (owner token, else default, never another)no-token, no requestunchanged

Open raw log URL, validated in the background. The content script's link href is only a hint. The background parses it with URL and accepts it only if the origin is https://github.com, the path is exactly /<owner>/<repo>/commit/<sha, 7–40 hex>/checks/<job digits>/logs, and owner, repo (case-insensitive) and job equal the route parsed from sender.url (the content-script frame URL that Chrome attaches to every content-script message, not the message payload), accepted only when its origin is https://github.com and it parses as an Actions job route (/<owner>/<repo>/actions/runs/<run>/job/<job>); a missing or non-matching sender.url is refused. It then rebuilds the URL from those parts (no query, no hash) and passes only that to chrome.tabs.create, using sender.tab.id only to place the new tab next to the page (openerTabId, index). Anything else is refused and the page shows "Could not open log".

Why not sender.tab.url (probed live during plan review). In the dedicated browser with the current manifest (permissions: ["storage"], host_permissions: ["https://api.github.com/*"]), chrome.tabs.query({}) from the service worker returns tabs with url: null, an open github.com tab included: content-script match patterns do not grant tab.url, and adding the tabs permission or a github.com host permission is out of scope. So neither the validation nor C6/R1 relies on tab.url.

The scope header is never used to decide. Detection runs only on a job page, switch on, token resolved, and only once the page shows the job concluded (an in-progress job could answer 404 and be misread as not-permitted). Anchors read from the live probe: route by URL; job status from the visible text under the job title in .CheckRun-header, matched whitespace-insensitively (all whitespace, including non-breaking spaces and newlines, collapsed to one space and trimmed before matching: live reads "failed  in 29s" with a double space; "Started … ago" for a running job); run status from the page-header icon's aria-label ("failed:", "currently running:") with the Summary "Status" value as second source; raw-log link by href /commit/<sha>/checks/<job>/logs (class js-steps-dropdown-raw-logs as a second match), never a CSS-module class. A missing anchor means no row, retried at the next scan.

Data, permissions, privacy

  • Manifest permissions: none new. chrome.tabs.create needs no permission; the Open raw log check reads the page route from sender.url (always present on content-script messages), never sender.tab.url, which is null without the tabs permission or a github.com host permission (probed live, see How it works); clipboard writes from the page in a click need none (check P1).
  • Token permission: none required, one optional. Fine-grained: Actions: Read-only plus access to the repository, only for Open raw log. Classic: unchanged; a repo grant already present is used as is; no text recommends repo or a write permission. Missing-permission state: no button, no Actions-page message, warning only in Options. Verify access: not extended (VB1; the token page relies on detection), so no "available since release" line is needed.
  • Requests: one read probe per repository and token per 60 s on job pages (plus one fresh probe per Open raw log click). Redirect not followed, target URL never read, stored or logged; no log bytes.
  • New storage keys: ghalsEnabled (boolean) and ghalsOutcomes = { "<owner>": { state: "ok"|"not-permitted", at: <ms> } }: no token, repository, URL, job ID or log. Cleared on any saved-token change and when the switch goes off (OL1: the stored-outcome design).

Risks and open questions

  • Signed out, or no raw-log link on the page: the page-link route has nothing to open, so Open raw log stays hidden even when detection says ok. Assumption, recorded on the issue (default: hidden; R1 records it as the one known disagreement).
  • Manual-redirect probe might not behave as expected for some token type (D1). Default: keep it fail-closed (anything but a redirect or 2xx is not ok); if it cannot distinguish, stop and report rather than add a metadata guess.
  • Expired or unavailable logs not declared on the page: the button can appear and the click's fresh probe (410 → unknown) shows "Could not open log". Accepted by the issue.
  • Timed-out jobs and runs: resolved by a live capture for this revision. A job that exceeds timeout-minutes ends with API conclusion cancelled and the annotation "The job has exceeded the maximum execution time of 45m0s"; its job header reads "cancelled Nov 3, 2026 in 45m 33s" and its run Summary "Status Cancelled" (public budgie-at/budgie run 41670304361, and two other repositories with the same result). So it never reads "failed" and gets --log. The rule is a whitelist: --log-failed only when the job header status word is exactly "failed", or for a run the header icon label is "failed:" or the Status value is "Failure"; every other word (cancelled, timed out, success, skipped, anything unknown) selects --log. The run-level timed_out conclusion (a run past GitHub's run limit) has no public example found (0 among eight large repositories); the whitelist sends it to --log whatever its wording.
  • In-progress runs: Copy is hidden until C6 proves a form; default stays hidden.
  • Slow detection: an answer after the 1500 ms first paint is applied only on the next view, so Open raw log can be missing on a first visit over a slow network. Assumption: stability over a late button (rejected: inserting it late, which moves Copy; reserving an invisible Open slot, which leaves a gap in every state without Actions access).

Out of scope

  • Go to failed step, "Failed steps: N", Download logs, log search, an alternative viewer, log analysis, storing or sending logs, any change to the native interface.
  • Any new permissions / host_permissions, any write request, any required token permission, an Actions check in Verify access.
