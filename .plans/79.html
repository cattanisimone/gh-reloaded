Release sequence (resolves PR #77)

Recommendation: do not merge #77 as 0.15.0. Fold #76 into 1.0.0. Release Please keeps one release PR on branch release-please--branches--main, so #77 is rewritten in place to "release 1.0.0": no parallel release PR, no conflicting tag.

Checked locally with the pinned release-please 17.6: from 0.14.0, a Release-As: 1.0.0 footer yields 1.0.0 alone, next to a feat, and inside a squashed multi-commit body. The repository squashes with the commit messages as the body, so the footer on this branch's last commit reaches main as long as the merge dialog keeps it. A footer is a one-time request (only commits since the last release count), so there is no config override to remove later.

Risks and open questions

  • The merge dialog may drop the footer if the body is replaced. (Default: the PR body says "keep Release-As: 1.0.0 as the last line"; if #77 does not turn into 1.0.0, a one-line release-as config PR, then a PR removing it right after the release.)
  • Ship 0.15.0 first instead? (Default: no, fold #76 into 1.0.0; one store review instead of two.)
  • Edit the manifest description for the store? (Default: yes, mention My Issues, still under 132 characters.)
  • The live smoke finds a broken feature. (Default: report it; blocking only for stability, privacy, data correctness or install problems, per the issue.)
  • PR type. (Default: chore: prepare the 1.0.0 release, hidden in the changelog; the footer, not the type, sets the version.)

Out of scope

  • New features (#78), redesigns, telemetry, licensing, permission changes, another release system.
  • Merging #77, creating tags or releases, store submission, the public website: maintainer actions.
  • Editing version or CHANGELOG.md by hand.
