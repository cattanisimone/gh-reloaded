#129 · Make the GitHub tokens settings clear

cattanisimone/gh-reloaded#129 · Size: normal · Goal: one token list with state and last test, a one-click Test per permission type, a side panel for add/edit, a discreet guide and a missing-permission warning, without changing how tokens are stored or chosen.

What changes for users

  • Settings → GitHub tokens becomes one list: a row per token (default + owner tokens) with name, Used for, state (Works, Missing permissions, Not tested, Not working, Can't verify, Not set) and last test (Today 09:12 · 4 of 5 OK).
  • Test on a row checks each of the 5 permission types on its own (at most 7 read requests) and opens the result under the row, with What should I do?, Test again, Check a specific repository.
  • Edit / + Add token open a 420 px side panel that reserves its space (the list reflows to its left, never under it) from 1024 px up, and a full-width sheet below 1024 px; a saved token is never shown again (Saved + Replace token); Save still applies everything at once.
  • Permission tables move into a closed Full guide under a 3-step box; Verify access disappears (its diagnostics live on as Check a specific repository).
  • A warning above the list appears when a feature that is on needs a type a token's last test shows as denied.

How it works

Test request plan (per row, max 7, sequential, stop on 401 / rate limit)

#RequestType proven
1GET /useridentity (401 → Not working, stop)
2Listing of a private repository, one result: default token GET /user/repos?visibility=private&sort=pushed&per_page=1; owner token (organization) GET /orgs/{owner}/repos?type=private&sort=pushed&per_page=1; owner token whose owner = login GET /user/repos?visibility=private&affiliation=owner&sort=pushed&per_page=1picks one repo R the token itself returns and checks R.private === true in the response. Empty list, 404, or private not true → requests 3, 4, 5, 7 are not sent and Contents, Pull requests, Issues, Actions logs are Not verified with "We can't tell why." (a public repository answers 200 without any permission, so it proves nothing)
3GET /repos/R/contents/ (status only, body discarded)Repository contents
4GET /repos/R/pulls?per_page=1&state=allPull requests
5GET /repos/R/issues?per_page=1&state=allIssues
6POST /graphql, one read query chosen by token and owner:
• default token, classic: viewer{projectsV2(first:1){totalCount}}
• default token, fine-grained (no owner known): viewer{organizations(first:10){nodes{login projectsV2(first:1){totalCount}}}}
• owner token, owner ≠ login (organization): organization(login:$owner){projectsV2(first:1){totalCount}}
• owner token, owner = login, classic: viewer{projectsV2(first:1){totalCount}}
• owner token, owner = login, fine-grained: not sent		Projects.
• Classic token (default or owner) or organization owner: data → Available; INSUFFICIENT_SCOPES / FORBIDDEN → Access denied; owner not an organization (NOT_FOUND) → Not verified "We can't tell why."
• Default fine-grained: any organization node whose projectsV2 answers → Available; no organization, or every node errors → Not verified, hint "We can't tell whether Projects can be read: GH Reloaded doesn't know which owner this token is for." Never Access denied (the token's resource owner may be an organization not listed, or the account itself) and never the classic-token hint.
• Owner = login + fine-grained → Not verified, hint "Projects owned by a personal account can't be read with a fine-grained token. Use a classic token with read:project." (no How to add it for a permission that cannot be added)
7GET /repos/R/actions/runs?per_page=1Actions logs (optional: no feature uses it today)

Token kind (for row 6): fine-grained when the secret starts with github_pat_, or when GET /user answers without an X-OAuth-Scopes header; classic otherwise. Read from the row's own token and response; nothing stored besides the outcome codes.

Warning text (exact)

  • Title: {feature} needs a permission your token doesn't have (or, with no test of that type yet, {feature} may need a permission your token doesn't have).
  • Body: Tokens: «{name}», «{name}». Features you already use keep working.
  • Detail, one line per missing type: GH Reloaded {version} uses {permission} (Read-only) for {feature}: {reason}. where {version} = chrome.runtime.getManifest().version, the installed version written by Release Please, and {reason} is the feature's sentence from the registry (e.g. "to show the status of linked pull requests"). It never says the version introduced the feature.

Data, permissions, privacy

  • Token permissions: none. No change to permissions / host_permissions; only api.github.com; REST GET only; one GraphQL POST with a query, no mutation; the row's own token only, no fallback to another token.
  • New storage: chrome.storage.session key ghrTokenTests = { [tokenId]: { at, codes: { contents, pulls, issues, projects, actions, identity } } } with codes available|denied|unverified|unchecked (+ sso hint flag). No GitHub answer text, no token, no repo name. Cleared by the browser on restart. chrome.storage.local keys untouched; a token whose secret changes or is removed drops its entry.
  • Later on the warning is page memory only. PRIVACY.md gets one sentence on the session-only codes.

Assumptions (recorded on the issue)

  • Five types incl. Actions logs: no feature reads Actions today, so it is always optional; kept because the issue fixes the set at five and it is the slot the next feature uses. Rejected: dropping it (contradicts "n of 5").
  • Version in the warning = chrome.runtime.getManifest().version, the release data Release Please writes; the registry holds no version literal. Rejected: a hand-kept "since" field (forbidden by the issue).
  • "May need" case = the stored record has no code for a type that a now-enabled feature needs (record older than the type). Session storage clears on browser restart and extension update, so this mostly appears after an in-session reload of a newer build.
  • Panel space: at ≥1024 px the panel reserves 420 px and the list reflows (stacked rows below 560 px of list width); below 1024 px a full-width sheet. Rejected: an overlay over the column (hides state and actions at 1100, plan review), a narrower panel (fields and the owner hint cramped below 360 px, and still ~260 px of list at 800). The issue's sheet breakpoint moves from 720 to 1023 because no side-by-side layout leaves a usable list below 1024.
  • Private repository proof: Test only checks repository types on a private repository the token lists; with none, those types are Not verified. Rejected: using a public repository (200 without permission would show Works with no proof).
  • Projects check per token: a default token has no owner, so it is never treated as a personal account. Default fine-grained: one GraphQL request over the viewer's organizations (first 10); any readable projectsV2 → Available, otherwise Not verified with "We can't tell whether Projects can be read: GH Reloaded doesn't know which owner this token is for." The classic-token hint is shown only for an owner token whose owner is the token's own login. Rejected: assuming a personal account for the default token (wrongly steers single-organization fine-grained users to a classic token), reporting Access denied from an organization node (the token's resource owner may be another one).
  • Owner-token listing: /orgs/{owner}/repos, or /user/repos?affiliation=owner when the owner is the token's login; a 404 or empty list makes repository types Not verified, never a scan.

Risks and open questions

  • A token with no private repository (e.g. limited to public ones) gets Can't verify when only repository types are required. (default: honest; Check a specific repository stays for a named repository.)
  • Token kind detection by prefix / X-OAuth-Scopes may miss a future token format. (default: unknown → classic rules, which can only produce Access denied from a GraphQL scope error GitHub actually returned.)
  • Large rewrite of options.js tokens code. (default: move logic into two pure modules; keep the save function and validation messages as they are.)
  • chrome.storage.session unreadable on the options page. (default per issue: page-memory fallback, declared in PR.)

Out of scope

  • Notifications permission sub-block and check (slot only).
  • Any change to token choice, priority, storage keys, new scope or host permission.
  • Automatic or scheduled tests; keeping test results across restarts.
