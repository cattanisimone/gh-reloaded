#126 · Check notifications beyond the current page when a triage category is selected

Revision 2: SSO caveat and 99+ cap, not-yet-looked-up items in label categories, behaviour by width, placement from live markup, reason-token tests.
Size: normal · Type: feat · Goal: when a triage category is picked, also check notifications outside this page through the Notifications API already in use, show matches in a separate read-only list, and make every count say what it covers.

What changes for users

  • Picking a category (Integrated, Quick bar) or clicking Check notifications outside this page (Grouped) reads more of your notifications through the API, a few pages at a time, with Stop and Load more.
  • Matches not on the page appear in a separate read-only Outside this page (k) list below GitHub's list and above its pagination; Grouped gets small sub-lists inside each section.
  • Counts read N+ while more remain unchecked and N only when complete. Every line says how many notifications were checked. Nothing ever says “all clear”.
  • When the API can't be used (no token, fine-grained token or missing scope, rate limit, error, an unsupported filter such as is:saved), the view says why and offers Review requests › / Mentions › narrowing links and Next page ›.
  • No new permission, no new storage key, no request to github.com, no writes. The cache lives in this tab's memory only.

How it works

Abort (query or URL change, turbo:before-cache, Stop, category change, module stop) bumps a generation counter: any answer of an older generation is dropped unread. REST pages go one at a time ≥ 250 ms apart; lookups 2 in flight, one 25-row batch per message, so the 12-batch cap is counted on the content side. Per fill: 4 REST pages, 12 batches, 8 s; ceiling 20 REST pages per query per tab (baseline pages included). Target: 10 matches for the selected category.

Data, permissions, privacy

Token permissions: none. No new scope, permissions or host_permissions; no new chrome.storage key. Requests: GET api.github.com/notifications with the default token, and read-only GraphQL lookups with the 1.7.0 token resolution. Items and facts stay in the content script's memory for this tab (120 s / 60 s), cleared on query change, native action, reload and module stop. Zero extension requests to github.com, no writes, no telemetry. PRIVACY.md gets the two clarifications quoted in the issue; the promises do not change.

Risks and open questions

  • is_done=false and API ordering may not match the web inbox (default: send it as specified; outside results are always labelled “checked”, never “your inbox”; record what the live check finds).
  • The native token for Participating and two reason: tokens (OR or AND) are unverified (default: an unrecognised token is “unsupported filter”; keep two narrowing links unless OR is confirmed).
  • Fine-grained token answer shape (403 vs empty 200) (default: both map to no-capable-token, never rate limit; covered by mocks).
  • GraphQL cost per 25-row batch (default: keep 25, log rateLimit.cost in the dev counters; lower the batch if above 5).
  • The evidence popover for API-only items (default: reuse it with the item's facts; tag without popover if facts are absent).

Out of scope

  • Reading inbox HTML pages; any write (Done, Save, Unsubscribe, mark as read) on outside entries; checkboxes or bulk actions on them.
  • Prefetch on load or in the background, persistence, account totals, telemetry.
  • The Options page for notification permissions; changes to #101 / #102 / #105 / #106 beyond the shared triage block and the issue's amendments.
