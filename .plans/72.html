#72 · Improve dependency graph layout and edge routing

cattanisimone/gh-reloaded#72 · Size: normal · PR title: feat: improve dependency graph layout and edge routing

Goal: make every dependency traceable (fewer crossings, no edge through a card, no shared top corridor, a straight critical path, stable positions after a refresh), choosing the engine from a measured benchmark, not from a guess. Relationships, edge direction and the critical-path computation stay exactly as they are.

What changes for users

  • Cards in a column are ordered to untangle edges (crossing minimisation) rather than by connection count.
  • Edges that skip columns run through free lanes between cards instead of all climbing into one corridor above the graph, and they never cut through a card.
  • The critical path is laid out as straight as the graph allows (same row where possible), so it can be followed by eye as well as by colour.
  • A card with many links spreads its arrows along its side (ports sorted by the other end) instead of piling them up on one point.
  • A refresh that adds or removes one card leaves the other cards where they were. Embedded and full-screen views show the same order. Cycles are drawn as clearly marked back edges, never hidden.

How it works

Phase 1: benchmark (dev-only, never shipped)

Every crossing and intersection is computed on the rendered path (each Bézier flattened to a polyline), so all candidates are scored the same way: what the user sees. Runs both Hide transitive ON and OFF, embedded and full-screen sizes, both alignment modes, and an "add one / remove one card or edge" step for stability (order inversions per column, mean card displacement). Timing: median and p95 over 30 runs.

Decision rule, applied in this order and written up with the numbers:
  1. Correctness gate: blocker strictly left of blocked, every displayed edge drawn, zero card overlaps, zero edge–card intersections on supported fixtures, deterministic output.
  2. Readability: rendered crossings, overlapping segments, critical-path straightness, viewport size versus today.
  3. Stability after a small edit, then latency (p95 under 50 ms at 80 nodes in Chromium as the target).
  4. Footprint and maintenance: bytes added to the content scripts, usable without a build step as a plain script under MV3 CSP, licence.
A custom candidate wins a near tie. If a library wins and would add more than 100 KB to the extension or needs a bundler or worker, I stop and post the numbers on the PR for a decision before Phase 2.

Phase 2: layout pipeline (shape shown for the custom candidate, the one I expect to win; the report decides)

Steps 1 to 4 do not depend on card size, so embedded and full screen share one order. The previous order lives in memory in content.js (never stored) and seeds step 4 on the next refresh, which keeps unchanged cards in place. Input stays the graph after the external and transitive filters, so selection, lineage, external modes and refresh need no change beyond reading the edges back from the new paths (same data-from / data-to).

Risks and open questions

  • The benchmark is large for one PR. Default: one PR, in two visible steps (benchmark commits and report first, then the engine), so the report can be read before the implementation.
  • Cycle rendering is new visible behaviour. Today a cycle collapses to column 0. Default: one back edge per cycle, chosen deterministically, drawn dashed under the cards with a "cycle" tooltip; all edges stay.
  • Dummy lanes can make the graph taller. Default: lanes reuse row gaps and empty slots first; the benchmark caps height growth at +25% versus today, else the lane spacing is tightened.
  • d3-dag is ESM only, Graphviz is WebAssembly. Default: both run in Node for the benchmark; shipping either is considered only if it clears the decision rule, with the 100 KB stop above.

Out of scope

  • Changing what is fetched, the critical-path computation, transitive reduction or external modes.
  • Recursion into grand-children, zoom or pan, drag to reposition cards, persisting positions.
  • The board dependency arrows feature (features/board-dependencies), which has its own routing.
