#110 · Make the CI on main green again

Size: simple (plan and implementation together) · Goal: stop the unit test runner from crashing intermittently on CI.

What changes for users

  • Nothing in the extension. Only a test file changes, so no release.
  • CI on main and on every pull request stops failing at random in the unit suite.

Root cause

RunWhat the log shows
main 99424a2 (40779241006)The unit suite stops after test 404, in release-please-config.test.js. There is no summary, no not ok line, and the step exits with code 1.
main 2f4dc58 (40545710241)not ok 27 - test/unit/release-please-config.test.js, uncaughtException: Unable to deserialize cloned data due to invalid or unsupported version.
PR run 40792266136Stops right after a test in the same file, the same way as the first run.
Local, Node 20.20.2Reproduced: 3 of 40 runs of that file crash with the same error.

On Node 20, node --test reads each test file's stdout as its binary message channel. release-please's default logger writes coloured info lines to that same stdout. When a log line lands inside a message frame, the parent fails to deserialize it. Depending on timing, it then reports the file as failed or crashes without a summary. That is why the log names no failing test.

Risks and open questions

  • The test reaches into release-please internals (build/src/util/logger.js). It is pinned at ~17.6.0, and the file already uses deep imports that fail loudly if they move. Default: accept this.
  • The PR type is test:, not the issue's fix(ci):, because users notice nothing and a fix would cut a patch release with no user-facing change. Recorded as an assumption.

Out of scope

  • Moving CI to Node 22. It is a wider change, and silencing the logger already removes the cause.
  • graph-bench's p95 timing budget can fail on slow local machines (it failed on the agent's aarch64 sandbox). It passes on CI and is listed as a follow-up.
