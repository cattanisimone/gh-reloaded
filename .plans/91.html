#91 · Linked-PR status row on Projects board cards, with a detail modal

Size: normal (new feature, new UI surface, new background module) · Goal: spot the board cards whose linked PRs need action, without opening each PR and without any "ready to merge" verdict.

What changes for users

  • On a Projects Board view, an issue card with at least one explicitly linked PR gets a thin row under its fields: PR #317 plus one text signal (Checks failed, Changes requested, …). Cards without a linked PR are unchanged, pixel for pixel.
  • Several PRs: a neutral aggregate, 2 linked PRs · 1 needs attention (2 PRs · 1 needs attention on narrow cards).
  • Click, Enter or Space on the summary opens a centred modal: one section per PR, Checks and Review shown separately, failing check names, a plain next-step line and a link to the PR.
  • Merged, closed and draft PRs are neutral; unverifiable data says Status unavailable, never green.
  • New switch Linked PR status in Settings → Features, on by default; it needs a token (same Pull requests: Read PR triage already documents), without one nothing is shown.

How it works

  • Card anchor (probed live on a public board, 2026-10-20): the un-hashed .board-view-column-card (it is role="button", tabindex="0", drag source); inside it, the fields list ul[aria-label="Fields"]. The row goes right after that list, in the same parent; with no fields list, at the end of the card's first child. No CSS-module class is read. If the card has no issue link, nothing is added and the next scan retries.
  • Association: only Issue.closedByPullRequestsReferences(first: 10, includeClosedPrs: true) (the issue's Development links, manual or closing keyword). No title or mention matching.
  • Per PR: number title url state merged isDraft reviewDecision repository{nameWithOwner} and commits(last:1){…statusCheckRollup{state}}. Failing check names are fetched only when the modal opens (contexts(first: 50)), so the board query stays small.
  • Native field: if the card already shows GitHub's Linked pull requests field (a field token whose tooltip or aria-label starts with "Linked pull requests", or a /pull/ link in the fields list), the row drops PR #N and shows only the signal, so numbers are not repeated.
  • Click vs drag: the row's controls are a real <a> and <button>; they stop click and Enter/Space keydown from reaching the card (no native side panel), but not pointerdown, so dragging from anywhere still drags the card. A click after the pointer moved more than 4px is ignored.
  • Budget: only cards in or near the viewport (IntersectionObserver) are queried; a key is re-fetched after 2 minutes or on SPA navigation; the board never waits (rows appear when data arrives).

Data, permissions, privacy

Reads issue↔PR links, PR state, review decision and checks rollup through GitHub GraphQL with the token mapped to the issue's owner (or the default one), never by trying every stored token. Nothing new is stored except the ghlpsEnabled switch; responses live only in memory (60 s shared cache plus a 2 min per-key cache in the page). No new permission or host. PRIVACY.md gets one line naming the new read.

Risks and open questions

  • Exact markup of the native Linked pull requests field on a card is unknown. (Default: detect by tooltip/aria-label text and /pull/ links in the fields list; the maintainer checks one card live.)
  • A PR in a repository the issue owner's token cannot see is not returned by GitHub, so it cannot be shown at all (not even as "unavailable"). (Default: accept and document; the row then reflects only readable PRs.)
  • Approved tone. (Default: neutral grey with a check glyph, so no colour ever reads as "go".)
  • Default on or opt-in. (Default: on, like PR triage; it costs nothing without a token and queries only visible cards.)
  • React re-renders may drop the row. (Default: idempotent re-insert on the next mutation scan, same pattern as Standup badges.)

Out of scope

  • Table and Roadmap views, the issue side panel, other Projects views.
  • Associations beyond explicit Development links (mentions, title or number matching).
  • Any write to Projects or PRs; mergeability or "ready to merge" signals.
