#75 · Per-token access diagnostics in Settings

cattanisimone/gh-reloaded#75 · Size: normal · Goal: each token card can check, on request, what that token can read on resources the user names, and say only what the API response proves.

What changes for users

  • Every token card (default and owner) gets a Verify access button next to Test. It opens a results panel inside that card, not a new page.
  • The panel asks for targets: a repository (required), and optionally an issue number, a Projects v2 URL and a private file. An owner card pre-fills the repository field with <owner>/. Nothing is probed until the user clicks Run checks.
  • Each capability gets one of five statuses: Available, Access denied (only when the response proves it), Not verified, Not checked, Temporary error. Each comes with the resource, the time, a one-line reason and, where it fits, a fix with a link to GitHub's docs.
  • Test still checks authentication only. Its success message now adds “Feature access not checked”, so it no longer reads as “all permissions granted”.
  • An edited, unsaved token is verified as typed and labelled Unsaved token. Editing the token or a target clears the old results.

How it works

The options page already calls api.github.com directly for Test. Diagnostics do the same, on purpose not through ghFetch/ghGraphQL: those resolve a token by owner, read the response cache and would fall back to the default token. Here the card's token is passed explicitly, and a failure is never retried with another credential.

Token type (fine-grained github_pat_ or classic ghp_) is read from the prefix only to choose which remedy wording to show, never to state a configuration. Rendered text is built only from the status code, those headers, GraphQL error type and our own wording; GitHub's message strings are matched, not displayed.

Data, permissions, privacy

  • No new permission: host_permissions already covers https://api.github.com/*. No new storage key; targets and results live in page memory only and disappear on reload.
  • Requests are user-triggered, at most 4 per run, all reads. Private file: only the HTTP status is used; the body is cancelled unread.
  • No token, Authorization header, response body or file content is rendered, logged or saved. A guard strips any occurrence of the token from rendered strings anyway (unit-tested).

Anchors: none on github.com. The change lives on the extension's own Settings page, so the CSS-module and fallback rules of section 3b do not apply; no github.com fixtures are added.

Live check: there is no github.com page to probe with gh-reloaded-live-dom. Instead I sent anonymous calls to api.github.com to check the response shapes the classifier depends on: a bad token gets 401, a missing repository gets 404 “Not Found”, an anonymous GraphQL call gets a 403 that is really a rate limit (the reason the 403 rule reads headers first), and X-GitHub-SSO, X-OAuth-Scopes, X-Accepted-OAuth-Scopes, X-RateLimit-* and Retry-After are all in Access-Control-Expose-Headers, so the page can read them. Not verified on live github.com: the SSO, fine-grained-denied and organization-policy 403s need a real organization and token. The maintainer should run Verify access once against an SSO organization and once against a repository left out of a fine-grained token's selection.

Risks and open questions

  • Do targets persist across reloads? Re-typing them is tedious. (Default: no, memory only, as the issue prefers. A later change could save targets, never results.)
  • Projects target format. (Default: paste the project URL, github.com/orgs/<o>/projects/<n> or /users/<u>/…; the URL says whether to query organization or user, so no guessing and no second query.)
  • Issues check without an issue number. (Default: GET /repos/o/r/issues?per_page=1; it confirms the issues list is readable, and the result says so. An issue number makes it a specific read.)
  • GitHub's 403 wording changes. The message matches that upgrade a 403 to “Access denied” are small and tested; an unknown 403 falls back to “Not verified”, the safe side.
  • Org approval pending vs not found. GitHub often answers 404 for both; that stays “Not verified” and lists approval as one possible cause.

Out of scope

  • Background or automatic checks, enumerating orgs/repos/projects, per-feature telemetry, writes to GitHub, token creation or permission changes, a standalone diagnostics page, persisting results.
