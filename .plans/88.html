#88 · Official GitHub Status in the header

Issue #88 · Size: normal · PR title: feat: show official GitHub Status in the header
Goal: a small, clearly attributed status dot next to the GitHub logo on every page, details one click away, and a notice only when an open incident concerns the page you are on.

What changes for users

  • A status dot right after the GitHub logo on every github.com page: green (no incident reported), amber (minor / maintenance), red (major / critical), gray hollow ring (unknown or older than 15 min). Never on top of the logo link.
  • Clicking it (or Enter / Space) opens a panel: overall status, only the affected components, open incidents with their latest update, "checked N min ago", the attribution GitHub Status · via GH Reloaded and a link to githubstatus.com.
  • An incident pill inside the header bar (placement B, no new row) only when an open incident hits a component relevant to the page (Actions on Actions pages, Pull Requests on PR pages, …) or has wide impact. Dismissible per incident update; the panel still lists it.
  • Settings → Features gets a GitHub Status switch (on by default); Settings → Advanced → GitHub Status gets Show incident notice (on by default).
  • No new permission for the user to accept (see Data, permissions, privacy).

How it works

  • One fetch for all tabs. summary.json alone carries the overall indicator, components, unresolved incidents and maintenances, so status.json is not needed. The cache lives in storage.session (survives service-worker restarts, in memory only, cleared with the browser) plus an in-flight promise, so ten tabs asking at once trigger one request. Tabs only ask the worker; the network is hit at most once per 5 min, and only while some github.com tab is open and visible.
  • Truthfulness. A snapshot older than 15 min (by our last successful fetch) or a feed never reached renders gray "Unverified" — the last good data is still shown in the panel, labelled with its age, never as a current green. A malformed body (schema check on every field we read) counts as an error. Errors keep the last good snapshot and retry with backoff 30s, 1, 2, 4, 5 min (a 429 honours Retry-After, capped at 15 min).
  • Relevance (relevance.js, pure, unit-tested): route → components. /actions, /runs/, /pull/N/checks → Actions · /pull/, /pulls → Pull Requests · /issues, Projects → Issues · /packages → Packages · /settings/hooks → Webhooks · /settings/pages → Pages · /codespaces → Codespaces · repo code routes (tree, blob, commits, compare, branches) → Git Operations · routes where a GH Reloaded feature calls the GitHub API (issues, Projects, repo pulls, /issues, .html blobs) also → API Requests. An incident is wide (notice everywhere) when its impact is critical, or it hits 3 or more of the core components (Git Operations, API Requests, Issues, Pull Requests, Actions, Webhooks). Impact none, maintenances and Copilot / Pages / Codespaces on unrelated pages: panel only.
  • Anchors, read from the environment, no CSS-module prefix: the dot goes right after header a[href="/"] containing svg.octicon-mark-github (aria-label "Homepage"), in the same flex row, no margin (the row's gap spaces it). The pill goes right before the header's search control, found by role / aria-label / visible text "search" within header. Missing anchor → nothing is inserted and the next scan retries; there is no other container fallback. Live probe: the signed-out header serves a.logo__<hash> (aria-label "Homepage") inside topRow__<hash>, a flex row.
  • SPA navigation. A throttled MutationObserver plus turbo:load / popstate re-ensure the dot and pill by id (never duplicated), recompute relevance when location.pathname changes, and remove the pill when the incident resolves or the route stops being relevant.
  • Dismissal stores {incidentId: updated_at}; a newer incident update shows the pill again; resolved incidents are pruned. Focus moves to the dot after dismiss.

Data, permissions, privacy

  • Sent: one anonymous GET https://www.githubstatus.com/api/v2/summary.json with credentials: "omit"; no token, no page URL, no user, repository or issue data (no query string, referrerPolicy: "no-referrer", sent from the service worker, never from the page).
  • Permission: none added. The endpoint answers access-control-allow-origin: *; I checked that an MV3 service worker with no host_permissions reads it (status 200, 12 components). A new host permission would make Chrome disable the extension on update until the user accepts it (a breaking change by our rules), so this keeps the change a feat. If GitHub ever drops CORS, the dot turns gray "Unverified", which is the designed degraded state. This differs from the issue's "only the www.githubstatus.com host permission is added", which the issue lets the reviewer revisit.
  • Stored: storage.local: ghgsEnabled, ghgsNotice, ghgsDismissed (incident ids + timestamps). storage.session: ghgsCache (public status data). No remote JS, no Statuspage widget.

Risks and open questions

  • Host permission vs CORS. Default: no new permission (above). Say so if you prefer the explicit permission; the PR becomes feat!:.
  • "Lightly severity-tinted bar". Tinting GitHub's whole header background conflicts with the gate "do not change colors of surfaces outside the notice area". Default: tinted pill + 2px severity line on the header's bottom edge, GitHub surfaces untouched.
  • Maintenance colour. The issue defines four colours. Default: an in-progress maintenance shows amber with the label "Maintenance"; scheduled (future) maintenance is panel-only and does not change the dot.
  • Signed-in header markup unverified live. Default: anchors only on the logo link + octicon and the search control (present in both header generations), both variants in fixtures; nothing is injected if they are missing.
  • Fallback A. Default: build B only. If the reviewer picks A, it is a rework of this PR: only the notice placement module changes, the status, relevance and dismissal logic stays.

Out of scope

  • Push / system notifications, telemetry, extra configuration beyond the two switches.
  • Inferring incidents not published on githubstatus.com; Statuspage widget or any remote script.
  • Shipping A and B as a user option, or a third placement.
  • Changing other features (e.g. reacting to their own API failures).
