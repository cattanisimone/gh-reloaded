#33 · Align Release Please with the versioning policy

cattanisimone/gh-reloaded#33 · Size: normal (release config, a new dev dependency and a new test) · Goal: the version Release Please picks matches the policy written in AGENTS.md.

What changes

  • Below 1.0, a breaking change (feat!:) gives 0.9.0, not 1.0.0.
  • The changelog has exactly three sections: Features, Bug Fixes, Performance. Every other type is left out and does not open a release PR on its own.
  • AGENTS.md gets a short guide to picking the PR type by what a user notices, plus the Chrome Web Store version rule.
  • Extension users see nothing new. Only version numbers and changelog headings change.

Policy: PR type → release

Measured with release-please 17.9.0 (the library behind release-please-action@v5), starting from today's 0.8.0.

How it works

release-please-config.json, top-level additions 
"bump-minor-pre-major": true,
"bump-patch-for-minor-pre-major": false,
"changelog-sections": [
  { "type": "feat", "section": "Features" },
  { "type": "fix",  "section": "Bug Fixes" },
  { "type": "perf", "section": "Performance" },
  { "type": "refactor", "section": "Refactoring", "hidden": true },
  … test, docs, ci, chore, build, style: hidden
]
AGENTS.md, "Version" bullet becomes a short sub-section 
- Version: … (a feat the minor, a fix the patch,
  a ! the major, or the minor while below 1.0) …
### Picking the PR type
- feat → minor · fix/perf → patch
- breaking (! + BREAKING CHANGE:) → major,
  minor below 1.0
- other types → no release
Chrome Web Store: 1–4 dot-separated integers,
always increasing, no pre-release suffix.

Test plan

A single unit test reads the repository's release-please-config.json through release-please's own config loader (Manifest.fromManifest, given a stub GitHub that returns the local files) and its strategy factory. That way the kebab-case keys are mapped exactly as in CI. The test then calls the strategy's versioning and changelog code on synthetic commits, starting from 0.8.0. Nothing goes over the network.

Risks and open questions

  • PR type. Nothing changes for extension users, so the PR is titled ci: align Release Please with the versioning policy, with no release of its own. (Default: ci.)
  • revert: commits. Because the issue lists exactly three sections, reverts are dropped from the changelog and do not release on their own. A revert of a released feature would wait for the next feat/fix. (Default: follow the issue. Say if you want a visible Reverts section.)
  • Version drift. The test pins release-please 17.9.0, while the action's @v5 tag can move. The test is only valid while both stay on the same major version. (Default: use a ~ pin and note it in a comment.)
  • Deep imports. The test imports release-please's build/src/… modules, which are not a public API. (Default: accept this. If an upgrade breaks it, the test fails loudly, not silently.)

Out of scope

  • Moving to 1.0 (maintainer's decision).
  • Changing the release workflow or the PR title check.
  • Rewriting existing CHANGELOG.md entries.
