#101 · Read-only classification engine and module registry for Notifications

cattanisimone/gh-reloaded#101 · Size: normal · Goal: a dormant, read-only engine on github.com/notifications that classifies each loaded notification into exactly one section, with evidence, for the later modules to display.

Open product decisions (asked to the maintainer, not decided by this plan):
  1. “Recent” direct mention: the issue does not define the window that makes a mention “Needs attention”.
  2. Team request, nobody has reviewed yet: no row of the issue's table covers it (not direct → not Needs attention; no review by another member → not Waiting).
  3. Banners vs “no visible change”: the plan reads the partial-data, missing-permission and rate-limit banners as state the engine exposes (text + retry time) for later modules to render, so this issue renders nothing.
The cells that depend on them are marked PENDING below.

What changes for users

  • Nothing visible: the notifications page stays byte-identical, and with no module enabled the engine does not even start (zero API requests).
  • Foundation for the later modules (reason tags + “Why is this here?”, filter bar, sections, configuration, options page): they register with the registry and read the engine's state.
  • The engine never writes to GitHub (no read / done / unsubscribe) and never hides or moves a row.

Classification contract

Exactly one section per notification; rules evaluated top to bottom; first match wins. Never “Needs attention” without evidence; when in doubt, “Unverifiable”.

Data, permissions, privacy

  • Reads: loaded rows of the page; PR reviewRequests, latestReviews, headRefOid (Pull requests: Read, already documented); GET /notifications (new, optional).
  • New optional permission: classic PAT scope notifications (fine-grained tokens are not accepted by that endpoint). Used through the default token, per the existing “no owner → default token, never try every token” rule. Missing → capability unavailable, partial banner state, everything else unchanged.
  • Stored (chrome.storage.local): ghntModules ({id: boolean}) and ghntNativeInbox (boolean). No notification data is stored; caches are in memory (60 s).
  • Writes to GitHub: none. No PATCH/PUT/DELETE exists in the code path (asserted by test).

“e2e harness” = the feature scripts loaded into the fixture page with a stubbed chrome.runtime, because the engine renders nothing the real extension could be asserted on. Live check: github.com/notifications redirects to login (probed: 302 → /login), so it cannot be opened anonymously. The fixture is built from GitHub's documented reasons and assumed markup; the PR will list it under “Not verified on live github.com” and ask the maintainer to check that rows, subject links, reason labels and pagination are found on their inbox.

Risks and open questions

  • Q1–Q3 above (asked; nothing implemented on those rows until answered).
  • Notifications markup unseen: collector may miss rows (default: a missing anchor yields no rows and no requests, retried on the next scan; never a fallback container).
  • Classic token may not be the default token (default: only the default token is used, per the existing rule; a later options issue can map it).
  • API coverage cap (default: at most 2 pages × 50 threads per load, in-memory cache 60 s).

Out of scope

  • Any UI for modules, the Native inbox control layout, options page, Verify access, README/PRIVACY (separate issues).
  • Marking read / done / unsubscribe; hiding rows.
  • Team membership checks; custom classification rules.
