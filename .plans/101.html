#101 · Read-only classification engine and module registry for Notifications

cattanisimone/gh-reloaded#101 · Size: normal · Goal: a dormant, read-only engine on github.com/notifications that classifies each loaded notification into exactly one section, with evidence, for the later modules to display.

Product decisions confirmed by the maintainer on the issue (2026-10-27):
  1. Recent direct mention: rolling 7-day window by default, configurable by the user. The mention itself must be proven inside the window: an unrelated thread update is not proof. Older proven mentions → Informational; insufficient evidence → Unverifiable.
  2. Team review requested, nobody has reviewed yet: Needs attention, flagged scope: "team" (shared attention, not a personal obligation) as opposed to scope: "direct". A review by someone else does not by itself make it Waiting: only PR/review evidence that the request was satisfied does.
  3. Headless: #101 renders nothing. It exposes classification, loading, partial-data, missing-permission and rate-limit state; downstream modules render banners, labels and controls. The acceptance criteria are read accordingly (see the test plan); the issue text itself was left for the maintainer to reword.

What changes for users

  • Nothing visible: the notifications page stays byte-identical, and with no module enabled the engine does not even start (zero API requests).
  • Foundation for the later modules (reason tags + “Why is this here?”, filter bar, sections, configuration, options page): they register with the registry and read the engine's state.
  • The engine never writes to GitHub (no read / done / unsubscribe) and never hides or moves a row.

Classification contract

Exactly one section per notification; rules evaluated top to bottom; first match wins. Never “Needs attention” without evidence; when in doubt, “Unverifiable”.

Team membership is not checked (it would need an org permission the issue does not grant). Instead, rule 6 requires at least one requested team that is pending right now (an empty team set never matches), that every team ever requested on the PR is still pending and that no direct request of mine was removed by hand, so whichever team brought me in is outstanding; when that cannot be shown, rule 8 says Unverifiable. The notification's updated_at is never used as the mention time.

TermDefinition
Counted reviewFrom reviews(last: 50) with state APPROVED, CHANGES_REQUESTED or COMMENTED. Excluded: DISMISSED and PENDING reviews, reviews by the PR author (e.g. an author's reply posted as a COMMENTED review), reviews by bots (author.__typename = "Bot"), and, for “by someone else”, my own. Rules 3–5 use counted reviews of mine only: a PENDING (unsubmitted) or DISMISSED review of mine on head never counts as reviewed.
Read set complete (review rules)Everything rules 3, 6 and 7 look at was read in full: reviewRequests(first: 100) totalCount ≤ 100, reviews(last: 50) totalCount ≤ 50, and the review-request timeline timelineItems(last: 100, itemTypes: [REVIEW_REQUESTED_EVENT, REVIEW_REQUEST_REMOVED_EVENT]) totalCount ≤ 100. Otherwise rule 8 (Unverifiable): with more than 50 reviews my review on head could be outside the window, and a false “no review of mine” would be a false Needs attention.
MeThe login signed in to github.com (meta[name="user-login"]), used only after it matched the token's viewer.login (rule 1). Tokens are per owner and can belong to another account, so the check runs per token.
Mention match@<my login> with word boundaries, case-insensitive: preceded by start or a non-[A-Za-z0-9_-]/non-/ character, and not followed by [A-Za-z0-9-] (so @alice does not match @alice-bot, @alicex or x@alice). Text inside inline code spans, fenced or indented code blocks and > block quotes is removed first. Items authored by me are ignored.

Mention window setting: stored as ghntMentionWindowDays (positive integer days, default 7; a missing or invalid value means 7). The engine reads it and re-classifies on change; the control that edits it belongs to the later configuration-panel issue.

Reason labels (collector)

The inbox shows the reason as lowercase display text, not as the REST value (observed on a logged-in inbox: commented, ci activity). collect.js maps the label with an explicit table: the label is trimmed, lowercased and its whitespace collapsed, then matched exactly. An unrecognised label gives reason unknown → rule 12 (Unverifiable, “unrecognised reason label”), with the raw label kept as evidence; it is never Informational and never becomes review_requested or mention. When a REST item from GET /notifications exists for the same owner/repo#number, its reason wins over the label.

Data, permissions, privacy

  • Reads: loaded rows of the page; PR state, reviewRequests, reviews, headRefOid, review-request timeline events (Pull requests: Read, already documented); for mention rows, comment/review bodies and times (Pull requests: Read / Issues: Read, the same read access the PR and board features use); GET /notifications (new, optional).
  • New optional permission: classic PAT scope notifications (fine-grained tokens are not accepted by that endpoint). Used through the default token, per the existing “no owner → default token, never try every token” rule. Scope proven missing (classic x-oauth-scopes) → missing-scope; otherwise missing → capability unavailable, partial banner state, everything else unchanged.
  • Stored (chrome.storage.local): ghntModules ({id: boolean}), ghntNativeInbox (boolean) and ghntMentionWindowDays (integer, default 7). No notification data or comment text is stored; PR, issue, comment and review text is read and matched in memory only; caches are in memory (60 s). PRIVACY.md is updated in this PR: the three keys are added to the “UI preferences” list, with a sentence that the engine reads PR/issue/comment text in memory only. Only the notifications scope text stays with the options issue.
  • Writes to GitHub: none. No PATCH/PUT/DELETE exists in the code path (asserted by test).

Risks and open questions

  • Several team requests on one PR with only some satisfied → Unverifiable (membership unknown); conservative by design.
  • Inline review-thread comments and items beyond the last 50 are not read: a PR with review threads or more than 50 comments/reviews never gets Informational from an old mention (rule 10 needs a complete read set); it is Unverifiable instead, unless a recent mention was found in what was read.
  • Notifications markup unseen: collector may miss rows (default: a missing anchor yields no rows and no requests, retried on the next scan; never a fallback container).
  • Classic token may not be the default token (default: only the default token is used, per the existing rule; a later options issue can map it).
  • API coverage cap (default: at most 2 pages × 50 threads per load, in-memory cache 60 s).

Out of scope

  • Any UI for modules, the Native inbox control layout, options page, Verify access, README/PRIVACY (separate issues).
  • Marking read / done / unsubscribe; hiding rows.
  • Team membership checks; custom classification rules.
