#106 · Configurable triage view with three layouts on the Notifications page

Size: normal · PR title: feat(notifications): add the triage view with three layouts · Re-plan of PR #109 (rev. 3) · Goal: see at a glance which loaded notifications need me, in the layout I pick, with GitHub's native inbox one click away.

Why a re-plan. The product contract of #106 and of the plan approved at 2ba1ac1 is unchanged. Two implementation review rounds in a row (on 91cd61a and 7601c9e) sent findings back into the same files (triage.js, triage.css), and each fix was local to the block or layout the reviewer measured, so the same defect came back in a sibling. This revision changes how the view is built (three structural rules below) so the whole class of defect goes away, and moves the coverage line to the top of the list, which is the one visible change to review.

New approach: three structural rules

RuleWhat it isDefect class removed
S1 · One view modelA pure M.view(counts, {layout, selected, collapsed, nextHref}) in triage-model.js returns everything any layout shows: per category label, count text (… when pending and 0), aria-label, pressed / expanded state, section note (none while pending), status line, empty text, coverage text, next link. The three renderers only map it to DOM; none formats a string or a count.R1: "done in one layout, missing in another" (C7, C8, C9). Unit-tested as one table: layouts × {loading, pending, partial, last page, empty, all classified}.
S2 · One block, one anchorEverything we add above the list is one element div[data-ghnt-triage="block"] placed right after the filter row (the anchor the #105 panel already uses): [pills or compact row] + status + empty state + coverage with Next page. Nothing goes before the first box or after the last box any more. Its left / right edges come from the filter controls (first child's left, last child's right, as insetsOf does today), written once to two CSS variables on the block and refreshed by a ResizeObserver on the filter row.R2: per-block alignment (C3). One measurement point, also correct after a resize, which today keeps stale insets.
S3 · Grouped builds once, then moves only what changed(a) While rows of the page are pending, the native list stays untouched and the block says "Classifying N…" (headers absent). (b) When nothing is pending, or after 2s at most, the sections are built in one pass (rows still pending then stay hidden and counted in "Classifying N…"). (c) Later renders move only rows whose section changed. (d) Scroll compensation runs only when scrollY > 0, anchored on the first on-screen header or row whose section does not change; at scrollY 0 nothing scrolls. overflow-anchor: none on the list as today.R3: double reorder and compensation at the top of the page (C10), without losing C11.

Kept from the branch as is: registry changes (unregister, start after prefs), collect.keyOf, the sidebar group and its CSS (C1, C2, C4–C6), the row-hiding filter, select-all guard, Turbo cleanup, the rebuilt fixture and the existing e2e tests. triage.js is restructured around S1–S3 (expected to get shorter: renderInfo, syncInfo, per-block insets and the per-render reorder go away).

What changes for users

  • Same as approved: a Triage module (on by default) sorts the loaded rows into Needs attention · Waiting · Informational · Unverifiable, in one of three layouts picked in the Triage ▾ panel: Integrated navigation (default), Quick bar, Grouped sections.
  • Changed in this revision: the coverage line ("Counts cover the N loaded notifications; more pages not loaded. Next page ›") moves from below the list to the block above it, next to the status. Users read the coverage before the counts it qualifies, and GitHub's own Prev / Next pagination stays at the bottom.
  • Changed in this revision: Grouped sections appear once classification of the page is done (normally under half a second), instead of reordering twice; the page never scrolls by itself.
  • Counts are always "of the N loaded", empty never reads as "all clear", no write to GitHub, no new token permission; Show native inbox restores everything.

Widths of nav[aria-label="Notifications"] as measured on the live page by the plan reviewer. The sidebar grows with the viewport, then shrinks at 1012px (GitHub's layout breakpoint), so the narrowest sidebar is 163px at 1012px, not at 768px. Label rule for every width: the item is a flex row, the label has min-width:0 + text-overflow:ellipsis, the counter is flex:none, so the counter (up to "99+") is never clipped. The narrow-mode switch is not a hardcoded breakpoint: the compact row is shown exactly when GitHub's own sidebar nav is not rendered (getClientRects().length === 0), re-checked on resize.

How it works

Grouped timeline (S3): load → rows pending → native list untouched, block "Classifying 4…", counts "…" → pending = 0 (or 2s) → sections built once, scrollY unchanged → later reclassification → only moved rows change place; scroll compensated only if the user has scrolled.

Risks and open questions

  • Coverage moves above the list, a visible change to the approved mockup (default: above, for the reasons in "What changes"; reverting it would bring back a second anchor and its own alignment rule).
  • Rows that never leave pending (engine error) would delay Grouped (default: build after 2s at most; still-pending rows stay hidden and counted in "Classifying N…", never shown as a category).
  • The reviewer's rounds report the controls at x=8 below 544px and at x=16 from 600 to 767 with slightly different wording (default: the rule is "same edges as the first and last filter control", measured, not a number; the fixture keeps the measured values).
  • Users who scrolled before classification lands see sections appear under them (default: S3 (d) keeps the first on-screen node in place).

Out of scope

  • Unchanged from #106: personal saved filters, full-text search, exclusions, advanced rules, token configuration, reason tags and "Why is this here?" popover.
  • Any change to the classification engine (#101) or the panel (#105).
