#106 · Configurable triage view with three layouts on the Notifications page

Size: normal · PR title: feat(notifications): add the triage view with three layouts · Goal: see at a glance which loaded notifications need me, in the layout I pick, with GitHub's native inbox one click away.

What changes for users

  • A new Triage module (on by default) sorts the loaded inbox rows into Needs attention · Waiting · Informational · Unverifiable, using the #101 engine as is.
  • Three mutually exclusive layouts, picked in the existing Triage ▾ panel (#105): Integrated navigation (default), Quick bar, Grouped sections. The panel's layout cards become selectable because the module now registers with them.
  • Integrated navigation and Quick bar filter the native list (rows are only hidden, never moved); Grouped sections reorders rows into four collapsible groups and puts them back when left.
  • Counts are always "of the N loaded", a partial page says so, an empty filter never reads as "all clear". No write to GitHub, no new token permission.
  • Triage off, or Show native inbox, removes everything and restores the original list and order.

Widths of nav[aria-label="Notifications"] as measured on the live page by the plan reviewer. The sidebar grows with the viewport, then shrinks at 1012px (GitHub's layout breakpoint), so the narrowest sidebar is 163px at 1012px, not at 768px. Label rule for every width: the item is a flex row, the label has min-width:0 + text-overflow:ellipsis, the counter is flex:none, so the counter (up to "99+") is never clipped. The narrow-mode switch is not a hardcoded breakpoint: the compact row is shown exactly when GitHub's own sidebar nav is not rendered (getClientRects().length === 0), re-checked on resize.

How it works

  • Registration: triage.js loads after content.js and calls GHNotifications.registry.register({ id: "triage", defaultOn: true, layouts: ["integrated","quickbar","grouped"], start, stop }). start(api) subscribes to the engine; registry.onChange reads registry.layout() and swaps renderer (unrender old → render new). No duplicate selector: the #105 panel already lists the layouts of a registered module.
  • Rows: each engine item has a key; collect.js gains keyOf(li) (same subjectLink/parseSubject logic it already uses) so the module maps key → li.notifications-list-item. Counts use in-page items only (API-only items cannot be shown, so counting them would not match the list).
  • Anchors (from the live probe, ARIA and stable classes only, no CSS-module class): sidebar nav[aria-label="Notifications"] → insert our nav[aria-label="Triage"] as its first child, before nav[aria-label="Inbox"]; quick bar / narrow row: after the filter row (the parent of the Group by / Sort by control, the same anchor the #105 panel uses); grouped: inside the native ul.js-navigation-container (in Box-body inside js-check-all-container), see Grouped mode. Anchor missing → nothing inserted, retried on the next scan; no other container.
  • Filter modes: non-matching rows get .ghnt-off (display:none); nothing moves. A rescan (new page, search, filter) re-applies. Pending rows are hidden while a category is selected and reported as "Classifying N…".
  • Grouped mode, one native list: no new ul. Rows stay in GitHub's own ul.list-style-none.color-bg-subtle.js-navigation-container, so the unread background, the check-all scope and GitHub's j/k/Enter navigation keep working. The four section headers are li.ghnt-sec inserted inside that list, and each row is re-ordered after its section header (a comment placeholder marks its native slot). Headers do not carry js-navigation-item, so GitHub's navigation skips them. A collapsed section hides its rows with hidden. With "Group by: Repository", where GitHub renders one list per repository box, the sections are built in the first box's list and the emptied boxes are hidden, restored on leave.
  • Keys across sections (GitHub's own handlers, not ours): j/k move through the rows in visual order, which equals DOM order, from the last row of one section to the first row of the next, skipping headers and collapsed rows; Enter opens the focused row; x toggles the focused row's native checkbox; e marks the focused row done, GitHub removes it and the count updates on the next scan. stop/layout switch puts every row back in place; stop/layout switch puts every row back in place. A row whose category changes moves without a scroll jump (scroll offset compensated around the move) and is highlighted ~3s (no animation under prefers-reduced-motion). Collapse state in chrome.storage.local.
  • Keyboard: all controls are native buttons (Tab order, Enter/Space). Category buttons use aria-pressed; section headers aria-expanded + aria-controls, ArrowUp/Down/Home/End move between headers. No single-letter keys are bound, so GitHub's shortcuts are untouched. Labels carry counts, e.g. aria-label="Needs attention, 3 of 25 loaded notifications".
  • Self-healing: a debounced observer (ignoring our own nodes) re-ensures anchors when GitHub re-renders the sidebar or list without a new engine state; render is idempotent so it cannot loop.

Data, permissions, privacy

  • Token permissions: none new. Reads only the engine's state; no request of its own; nothing written to GitHub (no read / done / unsubscribe).
  • New local key ghntTriageCollapsed {attention|waiting|informational|unverifiable: boolean} (Grouped sections only; default all expanded). Not removed by Restore defaults, which keeps the #105 contract of exactly three keys. The selected category is in memory only.

Risks and open questions

  • Moving rows in Grouped mode may break GitHub's row actions or bulk select. Default: rows never leave GitHub's native list, headers are extra lis in it, placeholders restore order; if a native action re-renders the list we rebuild. Flagged for the live review.
  • "Load more": GitHub's inbox paginates; it has no append. Default: the action follows GitHub's own Next page link and is labelled so; fetching and appending extra pages would need a new data path and is not done.
  • Category colours: red / yellow / blue / purple dots as in the issue mockups, from Primer's danger, attention, accent and done colours.
  • Overlap with #104 (reason tags, open): both touch manifest.json and collect.js; whichever lands second rebases.

Out of scope

  • Reason tags and "Why is this here?" (#102/#104), saved personal filters, full-text search, exclusions, new classification rules, token configuration and a Notifications permissions page, any write to GitHub.
