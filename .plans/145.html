#145 · One-sided files in one column in the Split diff

cattanisimone/gh-reloaded#145 · Size: normal (new UI surface, new feature, new settings switch) · Goal: in Split, a file whose changes are all on one side reads like Unified for that file only, automatically, with a per-file way back.

Revision 1 (plan review of 1cf06f7): options specs added to the test plan; the layout spec runs at 1500 / 1100 / 800 / 390 on all three pages plus dark theme, with the header and table assertions; the native header breakpoints are now measured values (Files changed, commit, compare). One deviation, recorded as an assumption: the table share is measured against the space left after GitHub's 40px number columns, since text ≥ 0.9 of the whole table cannot hold below 800px.
Revision 2 (plan review of a3a370b): header anchors are specified per page (file container, Viewed, More options, the … menu) by role, ARIA and visible text, measured live at 1500 and 390, with a test that the primary anchor is used at both widths; every row that is not a four-cell line row now has a stated treatment (colspan reduced, part of the line, not inspected, or anchor-missing), with a fixture row and a classify case each.
Revision 3 (plan review of 8e6a412): the count-based signature is gone, since a React thread mounted inside a hidden text cell changes no count. Every mutation inside a transformed table is now routed: a change inside a cell re-runs rule 4 on that row, added rows are classified, a structural change re-classifies the table, and our own writes are dropped (see “Late changes”). New late-thread e2e cases for both React markups (including a replacement that changes no count) and the classic rows, plus a per-row cost check on a 2,500-row table.
Revision 4 (plan review of 9c5a7b0): every table, transformed or not, keeps an incremental per-row summary, so a full re-classification runs only on a structural change; a cell or row change updates one row's contribution and re-decides in O(1) (see “Late changes”). Measured live: scrolling an 858-row two-sided diff mounts and unmounts no rows (0 mutations), while hovering mounts a text-free “Add comment” / “More actions” bar in the text cell, which rule 4 now treats as an affordance, not content. The way-back control is checked at every evaluation and on header mutations: re-inserted once when its anchor still exists, the table reverted with anchor-missing when it does not. Write order fixed: take pending records, process them, write, then takeRecords(). New e2e cost cases on a 2,500-row two-sided table and header-replacement cases on Files changed and commit.

What changes for users

  • On pull request Files changed, single commit and compare pages in Split, a file with only added lines (or only deleted lines) shows in one column: context lines once, GitHub's own highlight, line numbers kept (old + new for additions, old only for deletions).
  • Files with changes on both sides, tables GitHub already shows in one column, and anything in Unified are never touched.
  • Each transformed file gets a small Side by side button in its header (left of Viewed, or left of the … menu on commit/compare). It restores GitHub's Split for that file only and then reads One column. Not stored: a reload is automatic again.
  • Review threads, comment buttons, Reply and Resolve stay GitHub's: the extension only hides cells, it never moves or re-creates a node. A thread on the side that would be hidden keeps the whole file in Split.
  • New switch Split diff: one column for one-sided files under Settings → Features (on by default). No token, no request, no storage beyond the switch.

The reason is written to data-ghsoc-reason on the table, for tests and for a quick check in DevTools.

Layout: hide only, never move

  • data-ghsoc="additions|deletions" on the table; content.css hides, in four-cell rows only, cell 2 (additions) or cells 3–4 (deletions), plus the matching col and screen-reader th. Rows GitHub adds later (expanded context) are covered by the same CSS and re-checked by rule 4.
  • Full-width rows (hunk, classic hunk colspan=3) get colspan reduced to the visible count; the original value is kept in data-ghsoc-colspan and restored on revert. This is the only attribute written on GitHub's nodes.
  • Revert (button, rule 4 on a later evaluation, Unified, feature off) removes the attribute and restores colspans: GitHub's Split exactly as rendered.
  • Per table: one pass over rows on first sight, no network, no layout reads beyond the first row's rendered column count; no scroll listener. The pass also stores each row's contribution (a small record: change / empty / content per side, row kind) in a WeakMap and sums them into the table's summary; model.decide(summary) applies rules 2–5 in O(1). Later changes update the summary through the mutation routing below.

Late changes: incremental per row, full pass only on structure (rule 4 at every evaluation)

A React review thread is mounted inside the hidden text cell, with no row of its own, and can replace a child without changing any count, so nothing is skipped by comparing counts. Instead, one MutationObserver on the diff list (childList, subtree, characterData, attributes filtered to colspan) routes every record by where it happened, for every evaluated table, transformed or left in Split. Only a structural change costs a full pass; everything else updates one row's contribution to the summary and re-decides in O(1). The outcome flips (apply or revert) only when decide returns a different result.

Write order (every batch, and the first evaluation of a newly found table): (1) observer.takeRecords() and append them to the batch, so no GitHub record queued before our write is lost; (2) route and process every record, computing all decisions; (3) perform the writes (attribute, colspan, control) synchronously; (4) observer.takeRecords() and drop the result. No other script runs between (1) and (4), so what (4) drops is only ours. Records are handled in one requestAnimationFrame batch; a table with a table record gets one full pass and its row / rows records in the same batch are dropped.

Hover bar (observed live): hovering a line mounts div.addCommentButton (a button named “Add comment”) and div.action-bar-position (a button named “More actions”) directly in the text cell, and removes them on leave: 18 childList records for 12 pointer moves. They are row records (one row check each). For rule 4, a hidden-side cell is clean when it is empty-marked, or when its text equals the visible copy's text and it has no form field (textarea, input, [contenteditable]) and no element carrying text outside the line's code; an element subtree with no text and no form field (the hover bar) is an affordance, not content, so a pointer resting on the would-be-hidden side at load does not keep the file in Split.

Scrolling (measured live 2026-11-24, signed in, 1500px): on the Files changed of a public pull request with an 858-row two-sided .css file (React markup), scrolling through the whole table in 450px steps kept all 858 rows mounted and produced 0 mutation records, so no evaluation runs while scrolling. A 2,152-line lockfile in another public pull request is not rendered until Load diff, so it arrives as a late table (one full pass). Larger rendered files were not available live; if GitHub ever windows rows, they arrive as rows records, O(rows), never a full pass, as covered by the e2e cost test.

Budget: the full pass is the 100 ms one of criterion 14, and runs only on first sight and on a table record; a row record costs one row check (≤ 2 ms target on a 2,500-row table) whether the table is transformed or not. Each is wrapped in the feature's own performance.measure (ghsoc:full, ghsoc:row, ghsoc:rows, ghsoc:header) so the e2e tests read counts and durations directly.

Way-back control: kept present while it is needed

GitHub can re-render the file header (Viewed toggled, a file expanded after Viewed, reconciliation of the actions row) and drop our button while the table stays transformed. One column must never be left without its way back, so the control is checked for every file that has one (transformed, or Split by the user's click) at every evaluation batch and on every header record.

Per-file state

The user's choice is kept in memory per page URL + file path, so GitHub re-rendering the file does not undo it; reload or navigation forgets it.

Data, permissions, privacy

Token permissions: none. No request, no token, no new permission. Reads only the diff already in the page and changes only its presentation. Stored: the on/off switch ghsocEnabled (default on), like every feature; the per-file choice is never stored.

Assumptions (product choices the issue left open)

  • On by default, like the other no-permission features — rejected: opt-in, because the issue calls one column “automatic”.
  • Button text is the action (“Side by side” / “One column”, with a columns / rows icon); state exposed by aria-describedby (“Shown in one column” / “Shown side by side”) — rejected: aria-pressed with a changing label, because a pressed state on a label that flips reads backwards to screen readers.
  • A commit range inside a pull request (/pull/N/changes/<sha>, /pull/N/commits/<sha>) counts as Files changed — rejected: excluding it, because it is the same view and markup.
  • No header anchor → no transform (anchor-missing) — rejected: one column without the button, because the user must always have the way back.
  • At ≤ 767px viewport (GitHub's Viewed-label breakpoint, measured) the control shows its icon only, on all three pages, as Viewed does — rejected: hiding it, because the way back must stay; and keeping the label on compare's stacked row, because one rule on every page is simpler to reason about and test.
  • Header anchors are accessible names and roles (Viewed by its aria-label, More options by its labelled name, the compare menu by its View file item) — rejected: the visible “Viewed” text, because it is hidden at ≤ 767px, and header classes, because they are hashed.
  • Unknown row shapes and a classic comment cell crossing the left/right boundary make the whole file anchor-missing — rejected: hiding around them, because a guess about markup never seen live could hide content; GitHub's Split is the safe result.
  • A text-free element subtree with no form field in a hidden-side cell (GitHub's hover “Add comment” / “More actions” bar) is an affordance, not content — rejected: counting every element as content, because the pointer resting on a line at load would keep the file in Split and then flip it on mouse-out.
  • A Split table also switches to one column later when its last blocking row clears (a hidden-side thread resolved and removed) — rejected: deciding once at load, because the issue asks for rules 1–5 at every evaluation and that is the same rule in both directions.
  • “No newline at end of file” is treated as part of the line it marks — rejected: ignoring it, because a marker only on the hidden copy means the two copies differ.
  • The table's width contract is “fills everything that is not line numbers” (≥ 0.99 of table − number columns) rather than text ≥ 0.9 of the table at every width — rejected: the plain 0.9 ratio, because GitHub's fixed 40px number columns make it unreachable on additions-only tables narrower than 800px (0.78 at 390, measured), so it could only pass by shrinking GitHub's own columns.

Risks and open questions

  • Hiding a col plus cells in a fixed-layout table must not shift cells into the wrong column (default: display:none on cell, col and th plus colspan; the layout test asserts every column's x and width).
  • React may reset a colspan we changed when it re-renders (default: an attribute mutation on a reduced colspan triggers a full re-classification of that table, see “Late changes”).
  • Refined GitHub's same feature hides cells without changing col count (default: rule 1 also counts rendered columns; verified manually with both installed, issue open question 4).
  • Reply/Resolve clicked on a transformed file and the 100 ms budget are live/manual checks (default: report in the PR's Live check; a CI timing assertion carries its measurement in the failure message).
  • GitHub may make modified files one-column natively (default: rule 1 then leaves every table alone; the feature becomes a no-op).

Out of scope

  • Changing GitHub's Split/Unified preference or the layout of two-sided files.
  • Changing the comments interface; any persistence of the per-file choice.
  • Pages other than pull request Files changed, single commit and compare (Conversation-tab snippets, blob, blame).
